## Slide 1. 표지 - 20초

안녕하세요. 저희 6조가 개발한 프로젝트는 **Let's alarm**, 멀티 디바이스 실시간 동기화 알람 앱입니다.  
기본 구현 대상은 Android이며, Flutter로 앱을 개발하고 Firebase를 사용해 여러 기기 사이에서 알람 변경 상태를 공유하도록 구성했습니다.

## Slide 2. 목차 - 15초

발표는 먼저 프로젝트를 기획한 배경과 목표를 설명하고, 실제 UI 기능을 소개하겠습니다.  
그다음 전체 구조도와 기능 흐름, 주요 클래스 흐름을 통해 구현 방식을 설명한 뒤, 데이터 구조와 보안 요소를 짚고 시연으로 넘어가겠습니다.

## Slide 3. 프로젝트 개요 - 45초

기존 알람 앱은 보통 한 기기 안에서만 설정과 동작이 관리됩니다.  
예를 들어 여러 기기를 사용하는 상황에서 한 기기에서 알람을 수정하거나 해제해도 다른 기기의 상태는 그대로 남아 있을 수 있습니다.

저희는 이 문제를 해결하기 위해 Android 알람 앱을 먼저 구현하고, 로그인한 사용자가 같은 그룹의 여러 기기에서 알람 변경과 제어 상태를 공유할 수 있도록 설계했습니다.  
앱은 Flutter와 Dart로 구현했고, 계정과 공유 데이터, 변경 전달에는 Firebase를 사용했습니다. 이후에는 같은 저장 구조를 활용해 Web이나 PC 환경으로 확장할 수 있도록 고려했습니다.

## Slide 4. 주요 UI 기능 I - 알람 관리 - 45초

먼저 홈 화면에서는 현재 등록된 알람 목록을 한눈에 확인할 수 있습니다. 각 알람은 이름과 시간, 반복 설정을 보여 주며, 스위치로 빠르게 활성화하거나 비활성화할 수 있습니다.

알람을 추가하거나 수정할 때는 편집 화면에서 알람 이름과 시간을 지정하고, 반복 요일을 선택할 수 있습니다. 또한 소리와 진동 사용 여부, 다시 알림 사용 여부, 스누즈 간격과 횟수를 설정할 수 있습니다.  
즉, 기본적인 알람 생성과 편집 기능을 Android 앱에서 직접 수행할 수 있도록 구현했습니다.

## Slide 5. 주요 UI 기능 II. 울림과 계정 동기화 - 50초

알람 시간이 되면 울림 화면이 표시되고, 사용자는 `Dismiss`로 알람을 종료하거나 `Snooze`로 일정 시간 뒤 다시 울리도록 설정할 수 있습니다. Android에서는 잠금화면 상태에서도 전용 알람 화면이 나타날 수 있도록 구성했습니다.

또한 로그아웃 상태에서는 해당 기기에서 로컬 알람을 바로 사용할 수 있습니다.  
로그인한 뒤 그룹을 만들거나 참가하면 공유 알람 모드로 전환되고, 같은 그룹에 등록된 다른 Android 기기에도 변경된 알람 상태가 전달됩니다.

## Slide 6. 전체 구조도 - 75초

이 장표는 로그인 후 그룹 공유 알람이 동기화되는 전체 구조를 보여 줍니다.

먼저 기기 A의 Flutter Android 앱에서 사용자가 알람을 생성하거나 수정합니다. 이 알람은 기기 A에도 로컬 예약으로 등록되므로, 정해진 시간이 되면 기기 A 자체에서 울릴 수 있습니다.

그룹 공유 모드에서는 변경 내용이 Cloud Firestore에 공유 알람의 원본 데이터로 저장됩니다. Cloud Functions는 이 변경을 감지하고, FCM을 통해 등록된 다른 Android 기기에 변경 데이터를 전달합니다. 기기 B는 이 데이터를 수신한 뒤 자신의 Android 로컬 알람 예약을 갱신합니다.

여기서 중요한 점은 **FCM이 정각에 알람을 울리는 서비스가 아니라는 점**입니다. FCM은 기기 사이의 변경 전달을 담당하고, 실제 정각 울림은 각 기기에 미리 예약된 Android 로컬 알람이 담당합니다. 따라서 이미 예약된 알람은 인터넷 연결이 끊겨도 해당 기기에서 울릴 수 있지만, 새로운 변경을 다른 기기에 전달하려면 네트워크가 필요합니다.

## Slide 7. 기능 흐름 - 60초

위쪽 흐름은 알람 변경 동기화 과정입니다.  
기기 A에서 알람을 수정하면 공유 저장소에 반영되고, 변경이 감지된 뒤 FCM을 통해 기기 B에 전달됩니다. 기기 B는 전달받은 정보를 이용해 자신의 로컬 예약을 갱신합니다.

아래쪽은 알람이 실제로 울린 이후의 제어 흐름입니다.  
예약 시각이 되면 울림 화면과 소리, 진동이 동작합니다. 이때 사용자는 알람을 해제하거나 다시 알림을 선택할 수 있습니다. 해제를 선택하면 현재 울림이 끝나고, 다시 알림을 선택하면 설정한 시간 뒤에 다시 울리도록 예약이 바뀝니다.

로그인 후 그룹 동기화를 사용하고 있다면 이 제어 상태도 다른 기기에 전달되어, 같은 알람이 이미 표시되고 있는 기기의 상태를 함께 정리할 수 있도록 구현했습니다.

## Slide 8. 주요 클래스 흐름 - 75초

먼저 알람 생성 흐름입니다.  
사용자가 `AlarmEditorSheet`에서 정보를 입력하면 `AlarmListController`가 생성 요청을 처리합니다. 이후 `AlarmRepository`가 현재 사용 모드에 따라 데이터를 저장합니다. 로그아웃 상태라면 로컬 저장소를 사용하고, 로그인 후 그룹 모드라면 Firestore에 저장합니다. 마지막으로 알림 예약 서비스가 Android 로컬 예약을 생성해 실제 울림 준비를 마칩니다.

두 번째는 잠금화면에서 알람이 울리는 흐름입니다.  
Android에 예약된 시각이 도달하면 `LaunchRouterActivity`가 일반 앱 실행과 알람 실행을 구분합니다. 알람 경로인 경우 `AlarmActivity`가 전용 화면을 띄우고, `AlarmRingScreen`에서 소리와 진동, 해제와 다시 알림 버튼을 표시합니다. 사용자의 선택은 다시 `AlarmListController`를 통해 현재 예약과 동기화 상태에 반영됩니다.

이처럼 화면, 상태 처리, 데이터 저장, Android 알람 실행을 역할별로 분리하여 구성했습니다.

## Slide 9. 구현 진행 및 검증 현황 - 30초

Android 기본 기능으로는 알람의 생성과 수정, 삭제, 세부 설정, 로컬 예약과 울림 화면, 로그인과 그룹 동기화 구조까지 구현에 반영했습니다.

다만 두 Android 기기 사이의 실제 동기화 안정성, 해제와 다시 알림 상태 전달, 잠금화면 전체화면 표시, 네트워크 재연결 이후 반영은 발표 전 실기기에서 확인할 항목으로 구분했습니다. Web과 PC 확장은 Android 기본 구현 이후의 범위입니다.

## Slide 11. 데이터 구조와 보안 - 45초

공유 알람은 사용자와 그룹을 기준으로 관리합니다.  
`users`에는 사용자 정보가 있고, `members`에는 해당 그룹에 참여한 사용자가 저장됩니다. `alarms`에는 공유할 알람 원본 데이터가 저장되고, `devices`에는 변경 내용을 전달받을 등록 기기와 FCM 토큰이 관리됩니다. `commands`는 해제나 다시 알림 같은 제어 상태를 다른 기기에 전달하기 위한 구조입니다.

보안 측면에서는 Firebase Authentication으로 사용자를 식별하고, Firestore Rules를 통해 그룹 멤버만 공유 알람 데이터에 접근하도록 제한합니다. 또한 초대 코드는 그대로 저장하지 않고 해시 형태로 보관하며, FCM 토큰은 등록 기기 문서에서 관리합니다.

## 시연 전환 멘트 - 10초

지금까지 앱의 UI 기능과 동기화 구조, 내부 처리 흐름을 설명드렸습니다.  
이제 실제 Android 앱에서 알람 생성과 울림, 해제 또는 다시 알림, 그리고 그룹 동기화 동작을 시연하겠습니다.

## 시연 진행 순서 - 약 1분 30초

1. 홈 화면에서 알람 목록과 활성화 토글을 보여 줍니다.
2. 새 알람을 생성하면서 시간, 반복 요일, 소리·진동, 다시 알림 설정을 보여 줍니다.
3. 가까운 시간의 알람을 등록해 울림 화면과 `Dismiss` 또는 `Snooze` 동작을 보여 줍니다.
4. 가능하면 로그인 및 그룹 화면에서 공유 모드가 존재함을 짧게 보여 줍니다.
5. 두 기기 동기화가 현장에서 안정적으로 준비되지 않은 경우, 검증되지 않은 동작을 즉석에서 시도하지 말고 구조도 설명으로 마무리합니다.

## 예상 질문 대비

**Q. FCM이 알람을 울리나요?**  
아닙니다. FCM은 알람 변경이나 제어 상태를 전달하고, 실제 울림은 각 Android 기기의 로컬 예약이 담당합니다.

**Q. 인터넷이 끊기면 알람이 울리지 않나요?**  
이미 기기에 예약된 알람은 인터넷이 없어도 울릴 수 있습니다. 다만 다른 기기에서 새로 수정한 내용의 반영은 네트워크 연결이 필요합니다.

**Q. 로그인하지 않아도 사용할 수 있나요?**  
네. 로그아웃 상태에서는 해당 기기의 로컬 알람으로 사용할 수 있고, 로그인 후 그룹에 참가하면 기기 간 동기화 기능을 사용할 수 있습니다.

### 구조 및 패턴 질문

**Q. 이 프로젝트는 어떤 구조나 디자인 패턴을 사용했나요?**  
엄격한 하나의 아키텍처 이름을 붙이기보다는 역할을 분리한 구조로 구현했습니다. 화면은 사용자 입력과 표시를 담당하고, `AlarmListController`가 상태 변경 요청을 처리하며, `AlarmRepository`가 저장 방식을 추상화합니다. 실제 Android 예약과 알림 실행은 `AlarmNotificationService`와 네이티브 Activity가 담당합니다. 이 중 저장소 부분에는 **Repository 패턴**을, 앱 상태 연결에는 **Riverpod Provider 패턴**을 사용했습니다.

**Q. Repository 패턴을 사용한 이유는 무엇인가요?**  
로그아웃 상태에서는 `LocalDemoAlarmRepository`가 `SharedPreferences`에 저장하고, 로그인 후 그룹 동기화 상태에서는 `FirebaseAlarmRepository`가 Firestore에 저장합니다. UI와 Controller는 동일한 `AlarmRepository` 인터페이스만 사용하므로, 저장 방식이 바뀌어도 알람 화면 로직을 크게 바꾸지 않아도 됩니다.

**Q. Riverpod을 사용한 이유는 무엇인가요?**  
로그인 상태, 활성 그룹, 알람 목록, 동기화 상태, 현재 울리는 알람처럼 여러 화면이 함께 참조하는 상태가 있습니다. Riverpod으로 이 상태와 Repository 의존성을 제공하면, 인증이나 그룹 선택이 바뀔 때 연결된 UI와 저장소 선택을 반응형으로 갱신할 수 있습니다.

**Q. MVC나 MVVM으로 구현한 것인가요?**  
발표에서는 특정 패턴을 완전히 따랐다고 설명하기보다, Flutter UI와 Controller, Repository, Platform Service를 분리한 계층형 구조라고 설명하는 것이 정확합니다. ViewModel이라는 별도 계층을 엄격하게 정의한 구조는 아니며, Riverpod Provider와 Controller가 화면 상태 및 동작 요청을 연결합니다.

### Firebase 및 플랫폼 선택 질문

**Q. Firestore를 쓰는데 Cloud Functions와 FCM이 별도로 필요한 이유는 무엇인가요?**  
Firestore는 공유 알람의 원본 데이터를 저장합니다. Cloud Functions는 서버 측에서 변경을 감지하고, FCM은 백그라운드에 있는 다른 Android 기기에도 변경 정보를 전달합니다. 즉, 저장은 Firestore, 변경 감지와 전달 요청은 Functions, 기기 수신은 FCM으로 역할을 분리했습니다.

**Q. Firestore 실시간 동기화만 사용하면 되지 않나요?**  
앱이 열려 있을 때는 Firestore 변경 스트림으로 화면 상태를 갱신할 수 있습니다. 하지만 백그라운드나 잠금화면 상태의 다른 기기에도 변경된 알람 예약을 반영하려면 별도의 전달 경로가 필요합니다. 이 프로젝트에서는 FCM 데이터 메시지를 받아 Android 로컬 예약을 갱신하도록 구현했습니다.

**Q. Cloud Functions 없이 앱에서 바로 다른 기기로 보내면 안 되나요?**  
클라이언트가 직접 다른 기기의 토큰을 관리하거나 발송 권한을 가지면 보안과 관리가 불리합니다. Functions가 그룹의 등록 기기를 기준으로 서버 측에서 메시지를 전달하도록 하면, 클라이언트는 공유 데이터를 저장하는 역할에 집중하고 전송 권한과 대상 관리는 서버 영역에 둘 수 있습니다.

**Q. Flutter로 개발했는데 왜 Kotlin 코드와 Android Activity가 필요한가요?**  
일반 UI는 Flutter로 구현했지만, 잠금화면에서의 전체화면 알람 표시, Android 로컬 예약 트리거, 알람 전용 화면의 종료 동작은 Android 플랫폼 기능과 직접 연결됩니다. 그래서 `LaunchRouterActivity`와 `AlarmActivity` 같은 네이티브 경로를 두고 Flutter의 `AlarmRingScreen`으로 연결했습니다.

**Q. 전체 구조도에는 왜 로그아웃 상태의 로컬 모드가 크게 보이지 않나요?**  
구조도는 이 프로젝트의 핵심 차별점인 그룹 공유 동기화 경로를 중심으로 표현했습니다. 로그아웃 상태에서는 Firebase 경로를 사용하지 않고, 앱의 로컬 저장소와 Android 로컬 예약만으로 기본 알람 기능을 사용할 수 있습니다.
